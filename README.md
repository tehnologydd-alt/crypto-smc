# Orbit Signals — нативная Kotlin-версия для согласования

Приложение работает в двух режимах. В режиме «Телефон» оно обращается к публичным API Binance напрямую и хранит сигналы в SQLite телефона. В режиме «Сервер» оно получает сигналы, цены и состояние модели от Node-сервера Orbit по HTTPS; копия сигналов сохраняется на телефоне для просмотра без сети. Торговые API-ключи и автоматическая торговля не используются.

## Экраны

- **Рынок:** индикатор связи и резервной синхронизации, до 10 отмеченных пар, цена последней закрытой M1 на USDT-M фьючерсах и отдельный прогресс обучения двух стратегий.
- **Обзор актива:** свечной график M1–H4 со swing high/low, BOS, OB и FVG; масштабирование двумя пальцами и горизонтальная прокрутка; сигналы во вкладках «Ожидающие», «Активные», «Завершённые» с отдельной прокруткой и не более пяти видимых карточек; крупные сделки.
- **Сигналы:** вкладки «Все», «Отмеченные» (вручную выбранные сигналы) и «Завершённые»; рассчитанный вход, TP1–TP3, стоп и состояния. Завершённые карточки: серый — отмена или истечение, красный — стоп без TP, жёлтый — TP1/TP2 перед стопом, зелёный — TP3.
- **Статистика:** сравнение SMC и стратегии импульса, отдельные модели, прогресс обучения, достигнутые уровни, график результатов и архив старых сигналов.
- **Настройки:** переключение телефона и сервера, HTTPS-адрес и ключ доступа, контроль нагрузки, отмеченные активы, удержание экрана, отдельные уведомления для создания сигнала, входа, каждого TP и стопа; режим уведомлений только для выбранных сигналов.

В нижней панели три раздела; настройки открываются иконкой в шапке. Значки разделов и знак Orbit выполнены в едином векторном стиле.

## Мониторинг без сервера

При открытом приложении мониторинг запускается примерно раз в минуту. Android `JobScheduler` планирует фоновую проверку с периодом 15 минут и требованием сети. При следующей проверке приложение запрашивает пропущенные закрытые M1-свечи и воспроизводит события в порядке времени. После слишком длинного пробела активные сигналы получают состояние «Проверьте вручную».

Мониторятся только отмеченные активы. Если убрать актив, его прежние сигналы останутся в истории без новых событий до повторного добавления.

Android может отложить периодическую задачу. Когда пользователь принудительно останавливает приложение, фоновая работа не гарантируется до следующего запуска. Поэтому уведомления после закрытия могут приходить позже закрытия M1; гарантии непрерывной минутной доставки без сервера нет. Приложение не использует постоянную фоновую службу и не требует обхода ограничений батареи.

## Режим сервера и контроль лимитов

Для подключения нужен постоянно работающий Node-сервер из каталога `backend/`, доступный телефону по HTTPS. В настройках APK укажите домашний HTTPS-адрес, при необходимости внешний HTTPS-адрес того же сервера и один `APP_TOKEN`. В домашней сети приложение сначала пробует локальный адрес, вне Wi-Fi — внешний; при ошибке пробует второй. `127.0.0.1` на телефоне означает сам телефон. Ключ шифруется Android Keystore. Если сервер недоступен, приложение показывает последнюю синхронизированную историю и ошибку связи.

Сигналы телефона и их изменения автоматически передаются через единый `POST /api/mobile/sync`. Сервер подтверждает полученные идентификаторы и хранит историю в SQLite. Повторная передача не удваивает обучающие исходы. Импортированные старые исходы обновляют обучающие веса, но не считаются независимой проверкой точности сервера. Если база сервера создана заново, телефон определяет новый ID сервера и повторно отправляет всю локальную историю. Экран «Рынок» показывает активный маршрут, время последней связи и очередь передачи.

Локальный экземпляр можно запустить скриптом `backend/start-pc-backup.ps1`. Адрес сервера, ключ доступа и отпечаток сертификата задаются отдельно в настройках телефона; личные значения не следует публиковать в репозитории. Для удалённого доступа нужен защищённый HTTPS-маршрут к тому же серверу.

Сервер ведёт M1 по WebSocket, а закрытые M5–H4 сканирует через REST только для отмеченных пар на USDT-M фьючерсах. При 10 активах расчётное число запросов свечей M5–H4 — около 4 620 в сутки; реальное число может быть выше при восстановлении соединений и повторных попытках. Модуль `backend/limits.js` ограничивает REST-вес Binance по минутам и суткам, учитывает заголовок `X-MBX-USED-WEIGHT-1M`, а при HTTP 429/418 выдерживает `Retry-After`. В APK видны текущие счётчики сервера.

Текущий Node-сервер нельзя напрямую разместить как Cloudflare Worker: у него постоянные WebSocket-соединения и файловая/SQLite-база. Отдельная реализация на Workers потребует переработки мониторинга и хранения. Этот APK не включает развёртывание в Cloudflare.

Сервер продолжает мониторинг при закрытом APK. Нативные уведомления в этой версии появляются при следующей синхронизации телефона: примерно каждую минуту при открытом приложении и с задержкой от 15 минут в фоне. Для немедленных фоновых уведомлений потребуется отдельная интеграция FCM; веб-push старого сайта не доставляется напрямую в нативный APK.

## Две стратегии v4 и обучение

Новая реализация в Android и Node.js использует закрытые свечи M5, M15, M30, H1 и H4, подтверждённые свинги (2 свечи слева/справа), BOS по закрытию и разворотный CHoCH. Пробой требует тела не меньше 1,2 ATR14; OB — последняя противоположная свеча в пределах 8 баров и не шире 2 ATR; FVG — трёхсвечный разрыв шириной от 0,05 ATR. Срок жизни зон 12 баров, состояния: active, mitigated, filled, invalidated, expired.

Единая SMC-стратегия требует согласованной закрытой структуры старшего таймфрейма: H1 для M5–M30, H4 для H1, D1 для H4. Вход — середина OB; стоп за блоком, цели — 1R, 2R, 3R. Параллельная стратегия импульса требует первого пробоя диапазона 20 свечей, тела не менее 1,2 ATR, объёма не менее 1,5 среднего и закрытия в крайней четверти свечи при совпадающем направлении старшего таймфрейма. Её моделируемый вход — открытие следующей M1, если разрыв не более 0,25 ATR. Стоп — 1 ATR от входа, цели — 1R, 2R, 3R. Новые сигналы создаются только для USDT-M фьючерсов; старые спотовые сигналы доступны как архив.

У каждой стратегии отдельная обучающая модель и статистика. Старые сигналы и модели сохраняются в архиве. Восстановление событий идёт по закрытым M1; если порядок касаний внутри одной свечи неизвестен, первым считается стоп. Никакие реальные торговые заявки не отправляются.

Для сравнения на предоставленных **реальных исторических свечах** есть офлайн-команда `node backend/replay-rules.js /путь/к/свечам.json`. JSON должен содержать `market: "futures"`, `symbol`, `timeframe`, массивы `bars` (рабочий ТФ), `parentBars` (старший) и непрерывные `m1` — закрытые свечи с `time,end,open,high,low,close,volume`. Результат выводит раздельные окна development/validation/holdout (60/20/20%) и счётчики входов и TP. Он пока не учитывает комиссии, funding и проскальзывание, поэтому по нему нельзя судить о прибыльности.

### Лаборатория ПК v5 (теневой режим)

Откройте `/lab.html` на настроенном сервере. Лаборатория показывает воронку кандидатов SMC и «Импульс и пробой», долю входов, TP1 до стопа, истечения без входа, журнал кандидатов и покрытие архива закрытых свечей. Сервер сохраняет M1 из уже используемого WebSocket и полученные через REST закрытые свечи в таблице `market_candles` той же SQLite базы. Автономный движок телефона не меняется.

Новый `v5-shadow-1` фиксирует решение при создании серверного кандидата. Пока модель не прошла проверку, решение — «Сбор данных». После проверки кандидат проходит теневой фильтр только если оценка не ниже 60% и минимум на 5 процентных пунктов выше базовой частоты. Теневой фильтр **не подавляет живые сигналы** и не меняет обучение; старым сигналам не приписываются решения задним числом. Результат каждой группы станет сопоставимым после накопления независимых исходов.

В лаборатории можно запустить исследовательское воспроизведение для одного отмеченного актива на M5/M15/M30 за 3 или 7 дней. Сервер загружает только закрытые свечи Binance, проверяет непрерывность M1/рабочего/старшего таймфрейма и выполняет существующее сравнение двух стратегий с хронологическим разбиением 60/20/20. Запуск ограничен отмеченными активами, имеет 30-минутный кэш и использует общий модуль лимитов Binance. Он не создаёт живых сигналов, не меняет модель и не рассчитывает доходность: комиссии, funding, проскальзывание и фактическое исполнение ордеров в текущем воспроизведении отсутствуют.

## Сборка APK через GitHub Actions

При отправке изменений в ветку `review/android-apk` workflow `.github/workflows/android-apk.yml` запускает Kotlin-тесты, собирает APK и прикладывает его как `orbit-signals-debug-apk`. Для сборки обязателен секрет GitHub Actions `ORBIT_SIGNING_BUNDLE` с постоянным PKCS12-ключом. Номер версии возрастает по `GITHUB_RUN_NUMBER`. APK, собранные ранее с временными debug-ключами GitHub runner, придётся удалить **один раз** перед установкой первой сборки с постоянной подписью. Копия PKCS12 и пароля должна храниться вне репозитория: потеря ключа лишит возможности обновлять установленное приложение.

Для локальной сборки нужны JDK 17 и Android SDK 36. Выполните `gradlew.bat testDebugUnitTest assembleDebug`; результат появится в `app/build/outputs/apk/debug/app-debug.apk`.

Сигналы показывают касания рыночной цены, а не исполнение реального ордера на счёте. Автоматических сделок нет.
