# Orbit Signals — нативная Kotlin-версия для согласования

Приложение работает в двух режимах. В режиме «Телефон» оно обращается к публичным API Binance напрямую и хранит сигналы в SQLite телефона. В режиме «Сервер» оно получает сигналы, цены и состояние модели от Node-сервера Orbit по HTTPS; копия сигналов сохраняется на телефоне для просмотра без сети. Торговые API-ключи и автоматическая торговля не используются.

## Экраны

- **Рынок:** индикатор связи и резервной синхронизации, до 10 отмеченных пар, цена последней закрытой M1 на споте и USDT-M фьючерсах, уровень обучения 0–3.
- **Обзор актива:** свечной график M1–H4 со swing high/low, BOS, OB и FVG; масштабирование двумя пальцами и горизонтальная прокрутка; сигналы во вкладках «Ожидающие», «Активные», «Завершённые» с отдельной прокруткой и не более пяти видимых карточек; крупные сделки.
- **Сигналы:** вкладки «Все», «Отмеченные» (вручную выбранные сигналы) и «Завершённые»; рассчитанный вход, TP1–TP3, стоп и состояния. Завершённые карточки: серый — отмена или истечение, красный — стоп без TP, жёлтый — TP1/TP2 перед стопом, зелёный — TP3.
- **Статистика:** фильтр по рынку, ключевые показатели, полосы достигнутых уровней, график накопленной доли TP1 до стопа, прогресс обучения и компактная таблица результатов по всем активам из истории.
- **Настройки:** переключение телефона и сервера, HTTPS-адрес и ключ доступа, контроль нагрузки, отмеченные активы, удержание экрана, отдельные уведомления для создания сигнала, входа, каждого TP и стопа; режим уведомлений только для выбранных сигналов.

В нижней панели три раздела; настройки открываются иконкой в шапке. Значки разделов и знак Orbit выполнены в едином векторном стиле.

## Мониторинг без сервера

При открытом приложении мониторинг запускается примерно раз в минуту. Android `JobScheduler` планирует фоновую проверку с периодом 15 минут и требованием сети. При следующей проверке приложение запрашивает пропущенные закрытые M1-свечи и воспроизводит события в порядке времени. После слишком длинного пробела активные сигналы получают состояние «Проверьте вручную».

Мониторятся только отмеченные активы. Если убрать актив, его прежние сигналы останутся в истории без новых событий до повторного добавления.

Android может отложить периодическую задачу. Когда пользователь принудительно останавливает приложение, фоновая работа не гарантируется до следующего запуска. Поэтому уведомления после закрытия могут приходить позже закрытия M1; гарантии непрерывной минутной доставки без сервера нет. Приложение не использует постоянную фоновую службу и не требует обхода ограничений батареи.

## Режим сервера и контроль лимитов

Для подключения нужен постоянно работающий Node-сервер из каталога `backend/`, доступный телефону по HTTPS. В настройках APK укажите домашний HTTPS-адрес, при необходимости внешний HTTPS-адрес того же сервера и один `APP_TOKEN`. В домашней сети приложение сначала пробует локальный адрес, вне Wi-Fi — внешний; при ошибке пробует второй. `127.0.0.1` на телефоне означает сам телефон. Ключ шифруется Android Keystore. Если сервер недоступен, приложение показывает последнюю синхронизированную историю и ошибку связи.

Сигналы телефона и их изменения автоматически передаются через единый `POST /api/mobile/sync`. Сервер подтверждает полученные идентификаторы и хранит историю в SQLite. Повторная передача не удваивает обучающие исходы. Импортированные старые исходы обновляют обучающие веса, но не считаются независимой проверкой точности сервера. Если база сервера создана заново, телефон определяет новый ID сервера и повторно отправляет всю локальную историю. Экран «Рынок» показывает активный маршрут, время последней связи и очередь передачи.

На этом ПК резервный сервер запускается скриптом `backend/start-pc-backup.ps1` на HTTPS-порту 3443. Он создаёт отдельную базу, секрет и сертификат в каталоге `outputs/orbit-pc-backup` вне Git-репозитория. На телефоне укажите `https://<локальный IP ПК>:3443` в поле домашнего адреса, ключ из `connection.json` и SHA-256 сертификата из того же файла. Правило брандмауэра должно разрешать входящий TCP 3443 с домашней подсети для активного сетевого профиля Windows. На этом ПК профиль Public и правило `Orbit Signals LAN Backup` ограничено адресами `192.168.1.214` и `192.168.1.0/24`.

Для доступа вне дома можно установить Tailscale на ПК и Android, войти в одну личную сеть и запустить на ПК от имени администратора `tailscale serve --bg https+insecure://localhost:3443`. Полученный адрес `https://<имя ПК>.<имя сети>.ts.net` внесите как внешний адрес в APK. Tailscale шифрует внешний маршрут; `APP_TOKEN` остаётся обязательным. Это тот же Node-сервер и тот же API; Cloudflare Worker и его квоты здесь не используются. У текущего аккаунта Cloudflare нет домена для постоянного публичного hostname Tunnel.

Сервер ведёт M1 по WebSocket, а закрытые M5–H4 сканирует через REST только для отмеченных пар. При 10 активах и двух рынках расчётное число запросов свечей M5–H4 — 9 240 в сутки; реальное число может быть выше при восстановлении соединений и повторных попытках. Модуль `backend/limits.js` ограничивает REST-вес Binance по минутам и суткам, учитывает заголовок `X-MBX-USED-WEIGHT-1M`, а при HTTP 429/418 выдерживает `Retry-After`. В APK видны текущие счётчики сервера.

Текущий Node-сервер нельзя напрямую разместить как Cloudflare Worker: у него постоянные WebSocket-соединения и файловая/SQLite-база. Для отдельной реализации на Workers Free при 10 активах пришлось бы делать около 38 040 запросов Binance в сутки, а в минуту закрытия H4 один Cron запуск потребовал бы до 120 внешних запросов при лимите 50 на вызов. Поэтому этот APK не включает развёртывание в Cloudflare. Для него нужен отдельный проект Cron + D1 с распределением нагрузки и проверкой CPU.

Сервер продолжает мониторинг при закрытом APK. Нативные уведомления в этой версии появляются при следующей синхронизации телефона: примерно каждую минуту при открытом приложении и с задержкой от 15 минут в фоне. Для немедленных фоновых уведомлений потребуется отдельная интеграция FCM; веб-push старого сайта не доставляется напрямую в нативный APK.

## Стратегия и обучение

Сигналы создаются по закрытым свечам M5, M15, M30, H1 и H4. Требуются подтверждённый BOS, ордер-блок и незаполненный FVG в направлении пробоя. Для спота доступны только LONG-сигналы. Вход — середина OB, стоп — за OB, цели — 1R, 2R, 3R. События проверяются по диапазонам закрытых M1-свечей. При одновременном касании стопа и цели в одной свече первым учитывается стоп.

Модель обучается только после входа и исхода TP1 или стопа. Уровни: 0 — меньше 30 исходов, 1 — первые 30 исходов, 2 — достаточно новых проверочных исходов, 3 — ошибка прогноза минимум на 5% ниже базовой частоты. Уровень 3 может снизиться при ухудшении новых результатов. Старые сигналы веб-прототипа не включаются в новую локальную базу.

Крупные сделки считаются отдельно от стратегии: в обзоре видны сделки от 250 000 USDT среди последних 1000 агрегированных сделок Binance. Это ограниченная выборка последних сделок, а не точный объём всех крупных сделок за 15 минут или определение личности участника. Показатель не влияет на сигналы и уведомления.

## Сборка APK через GitHub Actions

При отправке изменений в ветку `review/android-apk` workflow `.github/workflows/android-apk.yml` запускает Kotlin-тесты, собирает APK и прикладывает его как `orbit-signals-debug-apk`. Для сборки обязателен секрет GitHub Actions `ORBIT_SIGNING_BUNDLE` с постоянным PKCS12-ключом. Номер версии возрастает по `GITHUB_RUN_NUMBER`. APK, собранные ранее с временными debug-ключами GitHub runner, придётся удалить **один раз** перед установкой первой сборки с постоянной подписью. Копия PKCS12 и пароля должна храниться вне репозитория: потеря ключа лишит возможности обновлять установленное приложение.

Для локальной сборки нужны JDK 17 и Android SDK 36. Выполните `gradlew.bat testDebugUnitTest assembleDebug`; результат появится в `app/build/outputs/apk/debug/app-debug.apk`.

Сигналы показывают касания рыночной цены, а не исполнение реального ордера на счёте. Автоматических сделок нет.
