# Orbit Signals — SMC / OB / FVG: спецификация стратегии v3

Статус: реализовано в ветке `feature/market-structure-v3` (Android Kotlin + сервер Node.js). Указанные правила являются фиксированной спецификацией; стресс-оценка требует отдельных реальных рыночных данных.

## 0. Область действия и инварианты

- Два независимых исполнителя, Android Kotlin и Node.js, **обязаны** выдавать одинаковые результаты для одной последовательности закрытых OHLCV-свечей. Общие тестовые наборы фиксируются JSON-фикстурами.
- Создание и сопровождение исследовательских сигналов, **без автоторговли** и без отправки заявок.
- Только отмеченные 1–10 пары к USDT; спот: LONG, USDT-M фьючерсы: LONG/SHORT.
- Для поиска сигналов: M5, M15, M30, H1, H4; M1 — мониторинг входа/TP/стопа. Данные старшего контекста: H1/H4/D1.
- Никакого look-ahead: используется только OHLCV с закрытием `end <= eventTime`. Состояние сигнала на момент его публикации неизменно; результаты не изменяют первоначальное решение.
- Все время в UTC epoch milliseconds; свечи и события обрабатываются строго по времени; дубликаты — по market/symbol/timeframe/swing id/event time.

## 1. MarketStructureEngine

### 1.1 Подтверждённые свинги

- Фрактал L=2, R=2. Swing High на баре `i`, если `high[i] > high[i-1], high[i-2], high[i+1], high[i+2]`; Swing Low — зеркально, строгие сравнения.
- Свинг становится виден алгоритму только после закрытия `i+2`. Повторные равные high/low не образуют два свинга; ничьи отвергаются.
- Каждый swing хранит `id, index, time, confirmedAt, kind, price`. Пробой по незавершенному/неподтвержденному свингу недопустим.

### 1.2 События BOS и CHoCH

- Пробой **только по закрытию**, а не по тени. Бычий пробой: `previous.close <= swingHigh.price && current.close > swingHigh.price`; медвежий — наоборот.
- Для исключения повторных событий один и тот же `swing.id` может быть пробит и учтен только один раз в одном структурном сегменте.
- Режим структуры: `range` (не определён), `bullish`, `bearish`.
- Первый подтверждённый пробой в range классифицируется как `BOS` и определяет направление. Пробой по ходу известного режима — `BOS`; первый пробой в противоположном направлении — `CHoCH` и переключает режим. Следующий пробой в новом направлении — `BOS`.
- CHoCH использует последний подтверждённый значимый противоположный откатный экстремум (в bullish — swing low, в bearish — swing high), а не произвольный минимум/максимум.
- Событие содержит `type (BOS|CHoCH), direction, level, swingId, occurredAt, structureBefore, structureAfter`.
- При двух противоположных условиях на одном баре не генерируем два события: классифицируем по фактическому закрытию; при неразрешимой двусмысленности сохраняем `range` и не публикуем сигнал.

## 2. ZonesDetector

### 2.1 Импульс / displacement

- ATR(14) — средний true range **14 уже закрытых баров, предшествующих бару пробоя**; если данных недостаточно, сигнала нет.
- Импульс совпадает с пробоем структуры и имеет тело `abs(close-open) >= 1.2 * ATR14`, причем свеча направлена в сторону пробоя.
- ATR и пороги фиксированы для v3; подбор на одном историческом отрезке запрещен как метод оценки качества.

### 2.2 FVG

- Бычий FVG трех свечей `a,b,c`: `a.high < c.low`, диапазон `[a.high, c.low]`. Медвежий: `a.low > c.high`, диапазон `[c.high, a.low]`.
- Ширина `>= 0.05 * ATR14` на момент формирования (ATR только из предыдущих доступных баров).
- Кандидат на сигнал должен быть того же направления, не заполнен на момент публикации и сформирован **не более чем за 3 бара до структурного пробоя, включая его бар**.
- Нет пересмотра `formedAt` и размеров старого FVG задним числом.

### 2.3 OB

- Последняя противоположная по цвету свеча не дальше **8 предыдущих баров** от импульса, породившего BOS/CHoCH и подтвержденный FVG.
- Границы OB: `[low, high]` выбранной свечи (полные тени). Ширина не больше `2 * ATR14`.
- `originEventId` обязательно связывает OB с пробоем; один и тот же бар не должен порождать множество дублирующихся активных зон по одному событию.

### 2.4 Жизненный цикл зон

Для **каждой** OB/FVG храним `active -> mitigated -> filled`, а также терминальные `invalidated`, `expired`.

- `active`: ни одна последующая закрытая свеча еще не задела зону.
- `mitigated`: после формирования тень последующего бара пересекла диапазон зоны, но не дошла до дальней границы заполнения.
- `filled`: для bullish-зоны `low <= zone.low`, для bearish `high >= zone.high`.
- `invalidated`: после пробоя противоположный CHoCH либо закрытие за защитным уровнем OB (для LONG `close < ob.low - 0.1*ATR_at_creation`, для SHORT зеркально). Проверка invalidation предшествует completed/filled при конфликте событий.
- `expired`: спустя **12 баров рабочего таймфрейма** зона неактуальна. Для анализа можно хранить её бессрочно в базе, но не использовать в новых сигналах.
- Сохраняем `createdAt, mitigatedAt?, filledAt?, invalidatedAt?, expiresAt, status` и причину. Запрещены обратные переходы статусов и `filled -> active`.

## 3. Context / RegimeFilter

- Старший ТФ: M5/M15/M30 -> H1, H1 -> H4, H4 -> D1; исключительно последняя подтверждённо закрытая свеча до времени сигнала.
- `BOS`-сигнал допустим только при совпадении с режимом старшего ТФ. Если режим HTF `range` либо данных недостаточно, сохраняем кандидата в диагностике, но не публикуем полноценный сигнал.
- `CHoCH` не считается готовым входом в противоположную сторону сам по себе: публикуется только после младшего подтверждения направления (закрытие последующего бара за уровнем CHoCH) и отсутствия противоположного активного HTF BOS. В остальных случаях — диагностический кандидат.
- ATR используется как фильтр качества данных (ATR > 0 и конечные цены). Сессии на крипторынке по умолчанию 24/7, отдельный фильтр часов выключен.
- В диагностике записываются все причины отказа: отсутствие HTF, нет импульса, слишком узкий FVG, устаревший OB, заполненная зона, противоречие режимов и т. д.

## 4. Execution & RiskManager (только исследовательский сценарий)

- При подтвержденном наборе MarketStructure + OB + FVG + Context создаётся `WAITING` сценарий; никакой реальной заявки.
- Плановый вход — середина OB; стоп для LONG: `ob.low - 0.1*ATR_at_creation`, SHORT зеркально; R = модуль разности entry и stop, TP1/2/3 = 1R/2R/3R.
- Сценарий живет не дольше **12 баров сигнального ТФ** до входа; не создаем одновременно два WAITING/OPEN/UNCERTAIN для одной market/symbol/timeframe.
- После публикации все события рассматриваются по закрытым M1 OHLC; касание лимитного входа и последовательность стоп/TP в пределах одного M1 неизвестны. Если касаются и стоп и цель, консервативно считаем стоп первым. Если в баре ожидания касаются и entry, и stop, не объявляем выполненный прибыльный вход.
- Актуальность зоны и актуальность сценария — разные сущности и хранятся независимо.

## 5. Данные, тестирование, принятие v3

1. Тестируем свинги без заглядывания в будущее, BOS и первый CHoCH, неудавшийся wick-пробой, одинаковые максимумы, чередование high/low, переход range/trend.
2. Тестируем OB/FVG: трехсвечную геометрию, минимальную ширину, 8-барный поиск, привязку к событию, частичную митигaцию, полное заполнение, invalidation, expiry.
3. Тестируем HTF: до подтверждения старшей свечи нельзя читать её close; отсутствие старших данных не может пройти фильтр.
4. Тестируем исполнение: gap через entry, конфликт TP/stop в M1, срок ожидания, отсутствие дублей, раздельные spot/futures.
5. Одинаковые JSON фикстуры должны проходить в Kotlin и JavaScript с числовой точностью; отображение Android/Web должно отмечать `BOS` либо `CHoCH`, а также `active/mitigated/filled/invalidated/expired`.
6. Валидация на последовательных отрезках в режиме walk-forward, с отдельным out-of-sample и разбиением по режимам рынка. Не переоптимизируем пороги по итогам каждого теста.
7. Схема v3 / модель v3 изолируется от v2: старая статистика, сигналы и исходы остаются читаемыми, но не смешиваются с новыми обучающими исходами. Миграция данных без удаления истории.
