# APEX 9 — этап 4: проверка устойчивости полезности источников

**Дата реализации:** 2026-11-11  
**Ветка:** `apex-provider-robustness-stage4`  
**Основа:** `apex-provider-forward-value-stage3` (без смены предварительно зарегистрированных правил).  
**Статус реальных результатов:** **COLLECTING**. Регистрация исследования — 2026-11-13 00:00 UTC; до этой даты реальные опубликованные сценарии не могут участвовать в новой выборке. Тесты используют исключительно синтетические сценарии.

## Что уже есть и не переписывается

В этапе 3 зарегистрированы три отдельных Spot-признака: Binance 24h, Binance видимый стакан и Bybit видимый стакан. Для каждого актива и TF (M15, H1, H4) выбираются первые 48 независимых опубликованных после регистрации M1/V2-сценариев, блоками по 16, исключительно по времени публикации и горизонту; результаты ранних блоков должны быть известны до начала следующих. На одинаковых наблюдениях сравниваются фиксированный базовый ранг и вариант с одним признаком. Модель не обучается и не меняет торговые решения.

## Что добавлено в этапе 4

`source-provider-sensitivity.mjs` получает **те же сохранённые пары**, что этап 3. Он не получает новых рыночных данных и не выбирает сценарии заново. Для каждого из трёх блоков после выполнения минимальных требований:

1. **Leave-one-out:** по очереди исключается ровно один из подтверждённых исходов, пересчитывается парное изменение AUC. Сохраняются минимум и максимум ΔAUC, чтобы увидеть, насколько показатель зависит от отдельной записи. Это **не доверительный интервал**.
2. **Сдвиг признака по времени:** неизменная последовательность исходов и базовых рангов сравнивается с циклическими сдвигами заранее сохранённого источникового знака на 1…N−1 позиций. Считается, сколько сдвигов показали не меньший ΔAUC. Это слабый негативный контроль, **не статистический p-value**.
3. **Проверка смещения состава исходов:** доля TP3 среди сценариев с измеренным источником сравнивается с долей TP3 среди всех завершённых решительных исходов того же заранее выбранного окна. Разница ≥20 п.п. помечается как фактор, способный исказить вывод. Дополнительно проверяется, что подпопуляция физически возможна внутри исходного окна.
4. **Защита:** неполные окна возвращают `COLLECTING`, неверные пары или невозможные счётчики — `CHECK_DATA`; неприменимые и устаревшие наблюдения не объявляются негативными. Не выдаются достоверность API или точность прогноза из наличия метаданных.
5. **UI:** сжатые численные результаты размещаются **в существующем раскрывающемся блоке источников**, под тем же провайдером. Отдельные страницы, постоянный polling и дополнительные API-запросы не создаются.

Кэш `APEX_SOURCE_COHORT_VIEW_V4` хранит только короткие диагностики (без сырых свечей, статей, токенов и архивных исходов). Старый V3 остаётся отдельным. Лимит чтения/хранения данных увеличен до 96 КБ с ограничением числа активов, чтобы вместить диагностику для избранного набора; обновление выполняется только по завершении уже существующего Room-аудита.

## Интерпретация

- `REPEATED_DESCRIPTIVE` из этапа 3 остаётся **только описательной ассоциацией**, не доказательством, что источник улучшает реальную торговлю.
- `sensitivity.caution=SENSITIVE` означает, что выявлена хрупкость к исключению наблюдения, сдвигам по времени или составу доступных исходов. `NO_FLAG_IN_THESE_CHECKS` означает лишь отсутствие этих **конкретных** флагов.
- **Операционная доступность API**, **согласованность контента поставщиков** и **добавочная описательная полезность** не подменяют друг друга.
- Отсутствующий источник — не ошибка прогноза. NEWS/SOCIAL/ONCHAIN/MACRO остаются метаданными без фиктивной оценки полезности, пока не будет фиксированного достоверного признака и отдельного зарегистрированного исследования.
- Модуль не рассчитывает вероятности выигрыша, доходность или статистическую значимость; не меняет веса агентов и не выставляет ордера.

## Что осталось для полного эмпирического завершения

После **2026-11-13 00:00 UTC** необходимо собрать фактические пострегистрационные M1/V2 сценарии на избранных активах до 48 непересекающихся публикаций на каждую TF. Данные каждого окна должны содержать хотя бы 12 свежих измерений и 10 завершённых TP3/STOP с минимум 3 исходами каждого класса. До этого никакие числа в отчёте не могут интерпретироваться как качество реального источника.
